# TokenRemain 项目工作流

先读根目录 [AGENTS.md](../../../AGENTS.md) 和 [pstack 适配规则](../../rules/tokenremain-pstack.mdc)。本技能组织步骤，不新增写入、委派、提交或发布权限。默认产物是任务自己的本地 diff 和证据。

在当前任务及其后续跟进中维持这些边界；用户更换任务时重新确认范围，用户退出本 mode 时停止套用流程。Cursor 才负责技能发现；不能声称仅写入文件就已完成插件安装或在其他宿主注册。

## 1. 写清任务合同

先读取指定计划和实际源文件，检查状态、分支、HEAD，以及任务相关 staged/unstaged diff。记录以下信息，避免把已有修改归为本次成果：

```text
目标与完成条件：
允许修改的模块/文件；明确排除项：
基准 commit；已有改动；本任务 diff 的识别方式：
已授权的 Git / 运行 / 外部动作：
验证入口与副作用等级：
```

以上是任务记录格式，填写实际内容即可，不必生成额外仓库文件。不要求用户重复提供可从代码、计划或会话推断的信息。

## 2. 按问题选择必要步骤

| 任务 | 工作顺序 | 交付要求 |
| --- | --- | --- |
| 调查或审查 | 阅读准确 diff/源文件；按需 `how`/`why`；追踪调用与证据 | 有引用的结论；不顺带修复，不触发提交/PR |
| 缺陷修复 | 同类环境复现或相关 fixture；定位机制；最小修复；重跑原用例 | 区分用例证明与真实应用复现；无法复现不声称已证明修复 |
| 功能 | 明确数据与行为合同；分析消费者；必要时 `architect`；实现；验证 | 用户可观察结果及受影响消费者 |
| 重构 | 固定当前行为；识别内部/外部 API；分步变形；做等价验证 | 不混入新行为，不删跨版本兼容路径 |
| 性能 | 同条件基线；测量/定位；一项假设；比较资源和新鲜度 | 前后证据；未改善的实验只撤回任务自有部分 |
| UI | 确认真实表面；复现状态和操作；修改；同表面验证 | 原生工具的交互与状态证据，不能只给静态截图 |
| 规则/文案 | 只改指定文件；校验链接、格式、约束一致性 | 无需产品构建；未经运行的验证配方明确标为草稿 |
| 发布 | 先确认发布对象、精确 commit、渠道和既有权限；采用仓库发布流程 | 本地构建、签名、公证、公开下载、设备安装分别证明 |

可用时读取所需的 pstack leaf skill/playbook，只采用不冲突步骤；跳过上游步骤时注明对应项目限制或不适用原因。不要调用顶层 `/poteto-mode` 再返回本 mode，避免路由递归。pstack、`cursor-team-kit` 或特定模型不存在时，直接使用当前工具完成对应步骤并披露缺失；不自动安装或伪造技能执行。

局部确定性改动不强制调用 `architect`、`arena` 或子代理。多个可行架构有实际权衡时才比较方案；协议、凭证、并发等变更适合独立审查。预算和可用模型来自当前任务及宿主，不能照抄上游默认模型。

### 设计阶段：检查异步等待边界

涉及登录、授权、请求、子进程、同步或持续 loading 时，先按 [DB-001](../../../docs/design-boundaries.md#db-001) 的决策卡写明超时选择及理由、结束状态的呈现、取消与资源所有权、迟到结果、部分完成和安全重试。没有总超时也必须说明退出机制；不能只在测试失败后补计时器。与等待无关的任务无需扩展这一步。

### 设计阶段：检查 UI 简洁性边界

涉及卡片、列表或信息面板时，按 [DB-002](../../../docs/design-boundaries.md#db-002) 明确常见内容、最窄宽度及附属状态。先评估尺寸/间距能否解决，再决定内层滚动、折叠或分页是否必要；记录对留白和整页阅读的影响。普通内容直接呈现，真正超出的内容保持可达。

## 3. 控制范围与并行

按 AGENTS.md R1、R7 分配所有权。只读研究和不共享写入的切片可并行；同一共享 Store、协议或运行实例由一个负责人处理。默认最多两个活动执行子代理，不能通过嵌套委派突破。

每次委派提供：目标、基线、AGENTS.md 和技能路径、允许修改的文件/hunk、禁止操作、已授权动作、验收条件、证据位置。父代理检查实际产物和测试输出，不转述“已完成”作为证明。

发现跨模块影响时先识别消费者。范围内必要改动一并验证；跨入明确排除项或其他仓库时，保留现有范围，报告依赖与未完成项，不假称端到端完成。新的 worktree 默认不包含未提交代码，迁移基线时必须明确。

## 4. 实现与验证

按任务合同做最小必要改动，遵守 R3–R6 的凭证、同步、行为、注释和生成文件约束。所有检查通过 [verify-tokenremain](../verify-tokenremain/SKILL.md) 选择对应入口。

异步功能同时落实 R12：UI 状态与实际执行对应，验证后再提交，取消/超时后的旧响应不能写入。按 DB-001 验证各退出路径，并隔离包括历史/派生缓存在内的真实写入出口。

测试失败先分类为本次回归、既有问题、环境限制或尚未确定，并保留当前证据。针对失败改动后复测；不能为绿灯改断言或 fixture。原生运行、安装和有副作用的脚本先检查授权与实例归属，缺少条件时继续源代码与测试工作，将运行验证列为未验证。

长任务开始前写完成条件、明确的有界预算和停止条件。每批只推进可验证单元，记录决定、理由、证据和结果。重复失败无新证据时按 R10 停止该路径；不自动创建后台定时任务或无限循环。

## 5. 自审与交付

检查任务 diff、未追踪新增文件、意外生成产物和工作区基线。`git diff --check` 不检查未追踪文件内容；新文件另做格式与链接检查。

有异步等待时，对照 DB-001 决策卡逐项自审：时限依据、超时呈现、取消能力、重试/迟到结果和测试隔离是否都有实现与证据；未覆盖项如实标注，不能用正常路径通过替代。

UI 改动按 DB-002 自审：常见内容完整可读、不产生多余内层滚动，长文案和真实溢出仍可达，整页滚动正常；不能用隐藏内容代替简化交互。

最终报告：

1. 改变了什么用户行为，或得到了什么调查结论。
2. 实际修改文件、关键选择与范围外依赖。
3. 定向/完整测试、运行验证的命令、结果和证据位置；明确失败、跳过和未验证项。
4. 是否保留原有改动，以及已执行或尚未授权的提交/发布步骤。

没有 Git 授权时以本地 diff 收尾；有授权则只处理任务自有内容，按已授权阶段继续。原生验证草稿、编译结果或 CI 状态不能替代发布产物证据。

## 维护此工作流

从真实失败或用户新约定提出最小规则修订，指向可执行契约；不堆积一次性环境细节。规则改动独立审查，检查规则、设计边界与技能入口互相一致。不要自动改写个人记忆、全局技能或模型配置。上游升级时按适配规则复核冲突点。
