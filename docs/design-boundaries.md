# TokenRemain 设计边界

本文件记录需要在功能设计时主动回答的问题，供项目 agent 和后续专用 pstack 工作流复用。它与 [AGENTS.md](../AGENTS.md) 一起使用，不新增提交、真实账号操作或发布权限；新增设计边界使用稳定编号，避免不同宿主各维护一份规则正文。

## DB-001：异步等待的退出、呈现与恢复

**适用范围：** 登录、授权、凭证验证、额度刷新、同步、上传下载、子进程、IPC，以及任何依赖外部结果而保持 loading 的功能。纯同步、立即完成的局部操作无需为了套模板增加计时器。

**起因：** 登录进程已停止，界面仍转圈；登录成功又被首次额度读取拖住。这类问题说明“底层应该会返回”不能作为界面退出等待的保证。设计需要同时回答：是否设置超时、什么条件结束等待、结束后用户看到什么、还有哪些工作可能继续执行。

### 1. 设计等待预算

- 列出等待对象、完成信号和所有者：哪个请求、回调、进程或系统对话框决定结束，哪个组件负责状态与清理。
- 明确是否设置总超时，以及时长依据：正常耗时、用户预期、外部服务约束、现有合同。历史实现里的具体秒数仅作案例，不是通用默认值。
- 分开考虑整次操作、各阶段与“多久没有进展”的时限。单次网络请求已有 timeout，不代表重试、多个请求、回调或进程输出读取组成的整条流程有上限。
- 总预算覆盖重试与阶段切换；不得无意中在每轮重试时重新获得完整预算。使用适合计算持续时间的时钟，明确睡眠/唤醒、切后台或重新打开界面后的处理。
- 不设置总时限的持续任务，必须说明为何需要持续运行，并设计可观察进度或存活检测、取消入口、所有者销毁后的处理。持续任务不应伪装成一个永远无法完成的短操作。

### 2. 先定义用户可见的状态

状态名称不要求各平台逐字一致，但语义需要覆盖：

| 状态 | 用户应该看到什么 | 操作与数据处理 |
| --- | --- | --- |
| 等待中 | 正在等待哪个步骤；有依据时展示进度或剩余时间 | 防止重复提交；耗时操作提供取消或离开入口 |
| 成功 | 已完成的目标 | 清除等待标记，恢复后续操作；非必要的后续读取单独显示状态 |
| 失败 | 可理解且准确的失败原因 | 退出等待；根据原因提供重试、检查连接或重新授权，不能一律要求重新登录 |
| 超时 | 本次等待已超时，以及可以采取的下一步 | 停止无限转圈、解除相关控件禁用；保留仍有效的旧数据，并标明读取时间/陈旧状态 |
| 用户取消 | 已停止等待或已取消操作，措辞取决于实际能力 | 允许重新发起；不把主动取消当作凭证错误或自动触发登录 |
| 结果待确认 | 等待已结束，但尚不能确认外部操作是否完成 | 提供查状态/恢复入口；未证明可安全重复前，不直接重新提交有副作用的操作 |

- 区分主要目标和附属读取。例如“登录成功，额度暂时未能读取”应保持已登录状态，提供额度重试；不能退回“登录失败”，也不能继续保留登录 spinner。
- 错误消息描述事实。网络超时不等于 token 无效；旧缓存可用不等于新请求成功。保留旧额度时不能伪造新的更新时间。
- 视图关闭或切后台时，明确任务是继续、暂停还是取消。外部浏览器登录不能仅因 app 切到后台就被取消；任务继续时应有可重新找到的状态和取消入口。
- 系统弹窗若无法由应用关闭，应说明由谁关闭、应用是否仅停止等待。不要承诺已终止实际上仍在执行的系统操作。

### 3. 状态必须对应真实执行

- 取消/超时应到达实际请求、子进程和回调桥接层；清理定时器、句柄、临时账号状态等任务自有资源。不能只隐藏 spinner。
- 覆盖“取消发生在启动前”“取消与成功同时到达”“进程结束但输出流仍未关闭”等竞态，保证完成通知至多一次、等待状态最终释放。
- 包装超时的异步结构本身不能继续等待一个不响应取消的子任务，否则计时器触发后 UI 仍可能卡住。无法取消的只读操作可以停止等待，但必须丢弃迟到结果，防止重试堆积后台工作。
- 在提交凭证、账号、缓存或 UI 状态前检查当前操作身份和取消状态；旧请求不能覆盖新请求，已经删除的账号不能被旧响应重新创建。
- 读取/验证与有副作用的提交分开。不能给写入套一个计时器就宣称安全：若超时后仍可能完成，必须设计“结果待确认”、查询或幂等恢复。取消不是自动回滚，也不授权删除用户原数据。
- 重试要有次数/时间预算，并沿用退避和错误分类；不得因为出现 timeout 就持续自动重试、刷新第三方 token 或弹授权框。UI 线程不能承担阻塞的进程、管道或授权读取。

### 4. 对应的验收证据

按实际风险选择相关用例，不要求每个纯文案任务运行产品测试：

| 场景 | 必须核对的结果 |
| --- | --- |
| 正常完成、显式失败 | 状态和提示正确，控件恢复，现有数据语义未变化 |
| 底层一直不返回或忽略取消 | 在设计的边界内结束界面等待；可取消/重试；底层限制如实表达 |
| 启动前取消、等待中取消、外部进程退出 | 完成通知不会丢失，任务自有资源被清理，无残留 loading |
| 取消/超时后迟到成功或失败 | 不写入已取消的凭证，不覆盖较新的结果，不复活已删除账号 |
| 重试、重复点击、离开后返回 | 不重复提交，不让旧结果关闭新一轮等待；恢复策略符合设计 |
| 主要目标成功、附属步骤失败 | 已完成目标仍保留，失败步骤有独立恢复入口 |
| 有副作用的请求结果未知 | 不误报“已取消/已失败”，不会通过重试重复执行 |

测试用模拟网络、CLI、时钟或回调时，要沿真实调用链检查所有写入出口：凭证存储、偏好、账号目录、主缓存、额度历史、其他派生缓存均使用任务自己的目录或替身；只替换请求函数不足以隔离测试。按影响验证真实用户状态没有被测试写入。

源代码证明、定向回归、全量测试与真实原生交互分开记录。原生验收观察“开始等待 → 超时/取消 → 操作恢复 → 再次尝试”，并核对迟到结果；单张截图、编译通过或仅等待真实服务碰巧超时都不足以证明这个合同。

### 5. 专用 pstack 接入合同

设计/architect 阶段填写下面的决策卡；实现阶段把状态和资源所有权对应到代码；review/verify 阶段用上述状态及竞态核对证据。简单功能可在任务记录中简写，不强制新增规格文件。与等待无关的任务注明不适用即可。

```text
DB-001 适用性：涉及哪些等待；不适用时写原因。
完成信号与所有者：谁决定结束，谁维护状态、取消与清理。
超时决策：是否需要；总时限/阶段/无进展时限及理由；重试预算。
界面状态：成功/失败/取消/超时/结果待确认时的提示、按钮与旧数据。
部分完成与生命周期：已完成步骤如何保留；关闭界面、切后台、重开如何处理。
取消与迟到结果：实际可终止到哪一层；提交点、当前操作身份和副作用恢复。
验收与隔离：覆盖用例、真实写入出口、证据位置和未验证项。
```

共享规则正文保持在本文件；Cursor 等宿主只增加发现入口和流程引用。这里定义的是可复用的设计/审查合同，不表示专用 pstack 插件已经安装或各宿主已经通过运行验证。

## DB-002：常见内容直接展示，避免不必要的交互复杂度

**适用范围：** 卡片、列表、信息面板及其滚动、折叠、分页和渐进展示设计。

**起因：** Limits 的统一卡片高度不足，只有两条额度时，重置时间、配速提示和更新时间仍会溢出，迫使用户在卡片内部滚动才能看全。此时应先给常见内容合理空间，而不是增加用户的操作负担。

### 1. 优先选择简单布局

- 先列清用户一次需要看到的信息及完整组成。对 Limits，包含标题/套餐、两个额度窗口、各自的重置与配速、更新时间；Codex 重置卡等附属内容也纳入检查。
- 优先调整共享卡片尺寸、间距和已有布局约束，使常见状态直接完整显示；比较增加高度带来的留白、网格一致性与页面可见内容，采用有实测依据的尺寸。基础高度以刚好容纳常见内容为准；少数长文案或附属信息优先按实际需要撑高，避免让所有卡片都留下大块空白。
- 需要滚动整页很正常；把少量内容再塞进一层小滚动区、折叠或分页，会增加阅读与操作成本。只有信息量、可访问性或任务流程确有需要时才增加这一层，并记录理由。
- 不通过隐藏更新时间/错误、裁切文字、过小字号、硬编码语言或服务商特例来掩盖空间不足。能局部解决的问题，不升级成新的自适应框架、展开状态机或额外设置。

### 2. 保留真正需要的溢出能力

- 常见内容装得下时，内层不应显示滚动条或截获本来用于整页的滚动手势。
- 多账号、多额度池、较长异常提示等可能超出常见布局；保留可发现且可操作的滚动/展开入口，重要状态仍须可达。不能仅因“两条进度条”就一律关闭滚动并裁切其他内容。
- 数据加载、账号切换、提示出现或消失后，重新核对适配；避免测量与滚动开关互相触发导致抖动，也避免为了统一高度无限扩张整页。

### 3. 验收与 pstack 接入

设计/architect 阶段先回答下面的决策卡；实现时优先选择最小布局改动；review/verify 阶段分别验证常见内容直接呈现和真实溢出仍然可用。小调整可把决定留在任务记录中，不强制新增产品规格或只断言尺寸常量的测试。

```text
DB-002 适用性与常见内容：用户一次需要看全什么；包含哪些标签、辅助信息和状态。
最简方案：尺寸/间距/层级如何调整；对网格、留白和整页可见内容的影响。
额外交互的必要性：为何仍需要内层滚动/折叠/分页；如果不需要，如何消除。
边界与可达性：最窄宽度、较长本地化、附属提示、多账号/多池、状态切换。
验收证据：无裁切、无多余内层滚动；整页滚动与真实溢出可用；未验证项。
```

原生 UI 修改要在真实表面检查：不能仅凭代码中的高度常量、编译成功或单张截图宣称滚动行为正确。与 DB-001 一样，本边界作为共享正文供未来专用 pstack 引用；不表示插件已安装或所有宿主已验证。
